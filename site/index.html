Clear means unencrypted. “Outside profile” describes drmr’s current implementation, rather than a limitation of the media formats.

  1. MP4 output contains one track, or the audio and video from the same qualified progressive source described below. Separate DASH/HLS audio and video tracks cannot be combined into one MP4 output.
  2. MP4 can store an audio start position and presentation duration in an edit list, for example to exclude encoder padding. Qualified progressive MP4 with one AAC-LC audio track and optional H.264 video preserves this playback range when converting from Clear, cenc, or cbcs to the MP4, DASH, and fMP4 HLS choices above. Complex edits and source DRM initialization metadata are outside this profile. See the full restrictions for the supported encryption layouts and presentation checks.
  3. TS input uses a limited profile of progressive H.264 video and 48 kHz AAC-LC audio. Audio-only input supports DASH, fMP4 HLS, and TS output. TS output with both video and audio uses separate playlists.

MP4 stores media. DASH (Dynamic Adaptive Streaming over HTTP) and HLS (HTTP Live Streaming) describe media segments in manifests or playlists. fMP4 means fragmented MP4; MPEG-TS means MPEG transport stream.

cenc uses counter-mode sample encryption; cbcs uses pattern encryption with cipher block chaining. HLS AES-128 encrypts whole resources; SAMPLE-AES encrypts selected bytes in TS media. DRM license acquisition and device playback need separate checks.

Starting with an HLS URL?

Only completed clear HLS is supported for URL acquisition. --download-dir is required: it retains the source for offline retries and independent verification. Remote MP4/DASH, encrypted URLs, live input, and byte ranges are outside this acquisition profile.

From declarations to checked media

Inspect what is declared, plan a supported route, then process the actual media. Keep the source for a separate verification.

  1. 1

    Inspect

    Read local MP4 metadata or DASH/HLS declarations. Media samples are checked during conversion and verification.

    drmr inspect source.mpd
  2. 2

    Plan

    Describe conversion choices and required tools. Conversion checks the actual media and keys.

    drmr plan source.mpd \
  --to cbcs --format dash
  3. 3

    Convert

    Repackage qualified media and compare it with the original before publishing a new output.

    drmr convert source.mpd \
  --to cbcs --format dash \
  --output converted \
  --keys-file keys.json
  4. 4

    Verify

    Run an independent comparison with the original source and the keys for each role.

    drmr verify converted/manifest.mpd \
  --source source.mpd \
  --keys-file keys.json --json

These commands illustrate a qualified DASH-to-CBCS-DASH route. Prepare an owner-only key configuration; do not put raw keys in command arguments or version control.

Four ways back to the original

A matching manifest is not enough. Media verification compares the result with its original across four distinct kinds of evidence.

Stream metadata
Compare the qualified codec, track configuration, and presentation properties.
Encoded packet content
Compare coded media payloads while allowing the supported packaging and protection changes.
Every packet’s timing
Compare absolute presentation time, decode time, and duration. No timing tolerance is used to hide a mismatch.
Complete decoded media
Decode the entire qualified presentation and compare the resulting pictures and audio.

Media proof has a boundary

Media verification checks content and timing using your supplied keys. DRM (digital rights management) license acquisition and playback on a device need their own tests.

Start with the CLI

Build from source with Rust 1.95 or newer. Windows is a native CLI target; use the Windows guide for PowerShell, paths, and protected files.

From a source checkout:

cargo install --path crates/drmr --locked
drmr --version
drmr doctor --probe --route progressive-mp4

The probe checks tool versions and advertised options. It does not verify a media asset.
