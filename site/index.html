Convert between encryption schemes

A command-line tool for converting between supported MP4, DASH and HLS encryption schemes, or to and from clear (unencrypted) media. You supply the required keys. Before finalizing output, drmr compares media content and timing against the complete source.

Clear means unencrypted. “Outside profile” describes drmr’s current implementation, rather than a limitation of the media formats.

  1. MP4 output contains one track, or the audio and video from the same qualified progressive source described below. Separate DASH/HLS audio and video tracks cannot be combined into one MP4 output.
  2. MP4 can store an audio start position and presentation duration in an edit list, for example to exclude encoder padding. Qualified progressive MP4 with one AAC-LC audio track and optional H.264 video preserves this playback range when converting from Clear, cenc, or cbcs to the MP4, DASH, and fMP4 HLS choices above. Complex edits and source DRM initialization metadata are outside this profile. See the full restrictions for the supported encryption layouts and presentation checks.
  3. TS input uses a limited profile of progressive H.264 video and 44.1 or 48 kHz AAC-LC audio. Audio-only input supports DASH, fMP4 HLS, and TS output. TS output with both video and audio uses separate playlists.

MP4 stores media. DASH (Dynamic Adaptive Streaming over HTTP) and HLS (HTTP Live Streaming) describe media segments in manifests or playlists. fMP4 means fragmented MP4; MPEG-TS means MPEG transport stream.

cenc uses counter-mode sample encryption; cbcs uses pattern encryption with cipher block chaining. HLS AES-128 encrypts whole resources; SAMPLE-AES encrypts selected bytes in TS media. DRM license acquisition and device playback need separate checks.

Starting with a media URL?

Use analyze URL --download-dir to retain and check supported MP4, static DASH or completed HLS. DASH requires one Period, SegmentTemplate addressing and an explicit finite SegmentTimeline. For encrypted input, supply --keys-file; key and license addresses are not fetched. The retained source supports offline planning, conversion and independent verification. See the guide for the media and acquisition profiles. Live input, byte ranges and other DASH addressing profiles remain outside this acquisition profile.

Convert a URL and keep its source

Analyze, plan, convert, verify

Retain and check the input, save one conversion, then execute it offline. Verify the current result against the retained original.

  1. 1

    Analyze

    Download a completed clear HLS presentation and check all admitted media tracks.

    drmr analyze \
  "https://example.com/vod/master.m3u8" \
  --download-dir source --json
  2. 2

    Plan

    Fix the source fingerprints, output format, protection, and new destination in a saved plan.

    drmr plan source/input.m3u8 \
  --to cbcs --format dash \
  --output converted \
  --save conversion.plan.json
  3. 3

    Convert

    Execute that plan with separately supplied keys. Changed source bytes are refused.

    drmr convert \
  --plan conversion.plan.json \
  --keys-file keys.json
  4. 4

    Verify

    Check the actual output format and protection, plus complete media and timing correspondence.

    drmr verify \
  --plan conversion.plan.json \
  --keys-file keys.json --json

This example converts supported clear HLS to CBCS DASH. Read the four-step guide and prepare an owner-only key configuration. For clear input and output, use --to clear and omit the key file. Use analyze --metadata-only for local or URL metadata without keys or retained downloads; it does not verify complete media.

For FairPlay HLS and Widevine/PlayReady DASH from one supported clear HLS transport-stream source, use plan --outputs outputs.json. The multiple-output guide covers the output list, separate keys, and required checks before publishing the complete result. Final manifests receive native Rust checks. Use verify OUTPUT --manifest-only to run native checks on saved output; add --external-validator to also run the Apple or DASH-IF tool for that format. Manifest validation checks are reported separately from complete media comparison.

Native checks and optional complete decoding

Rust independently compares every selected sample, codec configuration, clock and supported playback window with the original. Add --decode for complete decoding as an additional check.

Stream metadata
Compare the qualified codec, track configuration, and presentation properties.
Encoded packet content
Compare coded media payloads while allowing the supported packaging and protection changes.
Every packet’s timing
Compare absolute presentation time, decode time, and duration. No timing tolerance is used to hide a mismatch.
Additional complete decoding
--decode decodes the entire qualified presentation and compares the resulting pictures and audio. Unrequested decoding is reported explicitly.

Media proof has a boundary

Media verification checks content and timing using your supplied keys. DRM (digital rights management) license acquisition and playback on a device need their own tests.

Start with the CLI

Build from source with Rust 1.95 or newer. Windows is a native CLI target; use the Windows guide for PowerShell, paths, and protected files.

Check each release's Pre-release label and notes before use. See release compatibility for requirements and verification scope.

From a source checkout:

cargo install --path crates/drmr --locked
drmr --version
drmr doctor --probe --route progressive-mp4

The probe checks tool versions and advertised options. It does not verify a media asset.
