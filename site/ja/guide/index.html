1. はじめに

English

drmr は映像・音声の符号化データを維持しながら、ファイルの格納形式、配信形式、暗号化方式を変更するツールです。復号に必要な鍵を持つ技術者が、管理下のオンデマンドコンテンツを解析・変換・検証する用途を想定しています。画質を変更するエンコーダーや DRM ライセンスを取得するクライアントの機能はありません。

このガイドでは現在のソースで使える操作と対応条件を説明します。配布版を使う場合は同梱のドキュメントも確認してください。リポジトリ内の関連ドキュメントは英語で記載しています。実行例が成功しても、すべてのメディアや再生端末での動作を確認したことにはなりません。

公開版の CLI は GitHub Releases から入手できます。展開する前に、配布ファイルのハッシュを同じバージョンの SHA256SUMS と照合してください。外部のメディア処理ツールは別途必要です。配布対象と互換性の方針はリリースの説明（英語）に記載しています。

利用する配布物の Pre-release 表示と説明を確認してください。ソースからのビルド手順は CLI のインストールに記載しています。CLI の互換性と各バージョンの検証範囲は別に定めています。Web コンソールとデスクトップアプリは実験的な機能です。

これら四つのメディア処理は、既定で Rust による検査を行います。対象トラックの全サンプルまたは全アクセスユニット、コーデック設定、時刻、対応する再生範囲を読み取ります。--decode を付けると、コンテンツ全体のデコードも追加の必須条件になります。変換後の照合と独立検証では原本と実際の出力を別々に読み、以前の成功レポートだけでは判定しません。未対応の構造や、検証に必要な情報が不十分な入力は、どちらの検査範囲でも拒否します。圧縮データの一致と、その全体をデコードできることは別の性質です。後者の証拠が必要な場合に --decode を使います。メタデータのみの解析、--save なしの計画、マニフェストのみの検査では指定できません。

最短の実行例

最初の動作確認には対応条件を満たす非暗号化のローカル MP4 を使います。出力先の親ディレクトリをあらかじめ作成し、出力ファイルには既存のファイルと重複しない名前を指定してください。原本は変更されません。

入力が暗号化されている場合や出力を暗号化する場合は、第5章の手順でアクセス権を制限した鍵設定ファイルを渡します。この例でも、入力が対応範囲外なら処理は拒否されます。入力の確認や計画の保存に成功しても、その後の変換が成功するとは限りません。実行時に原本、鍵、ツール、指定した出力条件を改めて確認します。

主な操作手段は CLI です。依存ツールもまとめて実行したい場合は Docker を使えます。実験的な Web コンソールと Desktop では、同じ保存計画による解析・計画保存・変換・検証を操作できます。CLI の全コマンドを画面から実行する機能はありません。

暗号方式

AES は共通鍵暗号の名前です。CTR は counter mode、CBC は cipher block chaining の略で、どちらも AES の適用方法です。サンプルとは符号化された映像の一枚や音声フレームなど、処理の単位になるデータです。

部分サンプル暗号化はコーデックのヘッダーなどを平文のまま残し、サンプルの一部を暗号化する方式です。CTR/CBC の選択や、暗号化するブロックとスキップするブロックのパターンとは別の区分です。cenc と記載されていても、ファイルの全バイトが暗号化されるわけではありません。

cbcs と HLS AES-128 はどちらも CBC を使いますが、適用単位とメタデータが異なります。fMP4 HLS の CBCS と、FairPlay 向け TS の SAMPLE-AES も同じファイル形式ではありません。方式名を置き換えるだけでは変換できません。

これらの違いは W3C の MP4 暗号化説明、RFC 8216 の暗号化宣言、Apple の SAMPLE-AES 説明にも記載されています。一次資料のリンクは第18章にまとめています。

DRM システムと暗号方式の違い

Widevine、PlayReady、FairPlay は、鍵の取得や利用条件、プレーヤーとの連携を含む DRM システムです。drmr は既知の鍵を使ってメディアを変換し、対応する経路では必要なシグナリングを格納します。シグナリングとは、プレーヤーが DRM システムや鍵の場所を判断するための付加情報です。

複数の出力を作る場合も、共通の plan、convert、verify を使います。出力一覧で、Widevine/PlayReady 向けの DASH、FairPlay 向けの HLS をそれぞれ指定できます。PSSH は Protection System Specific Header の略で、DRM の初期化情報を格納するデータです。鍵設定と出力一覧の具体例は第5・6章に示します。単一出力の PlayReady 設定も引き続き使えます。

暗号方式の変換、シグナリングの整合性確認、ライセンス取得、実機再生はそれぞれ別の確認事項です。メディアの検証に成功しても、対象機器でそのコンテナ形式・コーデック・暗号方式・DRM の組み合わせを再生できるとは限りません。サービスで配信する前に、実際に使うライセンスサーバーと機器で確認してください。

cens と cbc1 は解析で識別できる場合がありますが、現在の変換先ではありません。対応表の「対象外」は drmr の現在の実装・検証範囲を表し、その形式で技術的に実現不可能という意味ではありません。

MP4 の有限音声範囲

このガイドでいう「有限音声範囲」は、MP4 の編集情報で音声の再生開始位置と長さが指定されている状態を指します。別の入力形式の名前ではありません。エンコーダーの初期遅延や末尾のパディング（長さを調整するための余分なデータ）を再生から除外するために、一般的な MP4 でも使われます。

対応する入力は一つの完全なプログレッシブ MP4 に AAC-LC 音声トラックを一つ含むものです。H.264 映像トラックも一つまで含められます。音声の格納識別子は mp4a、映像は avc1 です。音声の編集情報は通常速度での連続した一範囲を指定し、開始位置が負でなく、長さを音声クロックの整数値に正確に換算できる必要があります。

Rust で入力を所有者専用の作業ファイルにコピーし、各サンプルを元の位置で復号します。暗号化情報の領域をゼロで埋め、サンプルの配置、時刻、再生範囲を保持します。FFmpeg、デコード、再セグメント化は使いません。

TS の入力条件

TS 入力の対象は配信内容が確定した HLS です。番組構成が一つに固定されている必要があります。映像はプログレッシブ H.264 を一つ、音声は 44.1 kHz または 48 kHz の AAC-LC を一つまで含められます。同じ条件なら、音声のみの入力から DASH、fMP4 HLS、TS を出力することもできます。

TS パケットは 188 バイトです。映像の復号設定を表す SPS/PPS は途中で変更できません。AAC は 7 バイトの ADTS ヘッダーを使い、チェックサムを持たず、一単位に音声フレームを一つ含む必要があります。サンプルレートとチャンネル構成も途中で変更できません。複数番組、設定変更、壊れたパケット、時刻カウンターの周回、不連続、インターレース映像、未対応の記述子などは拒否します。

音声のみのプレイリストでは、最終区間の EXTINF が最後の AAC フレームの途中で終わる場合もあります。宣言の精度から再生する音声サンプル数を一つに決められる場合は、符号化された最終フレームをすべて残し、指定された再生範囲を HLS・DASH 出力に引き継ぎます。精度不足で複数の範囲が当てはまる指定、途中区間の短縮、丸ごと一フレーム以上を除く指定は拒否します。別の音声プレイリストを映像に組み合わせることはできますが、映像・音声を多重化したプレイリストでは音声だけの短縮範囲を宣言できません。この編集形式は HLS・DASH のマニフェストと組み合わせて検証します。同じ編集を持つ単一 MP4 の入力・出力は、独立した検証経路をまだ実装していないため拒否します。

SAMPLE-AES 入力では暗号方式を途中で変更できません。鍵形式は identity または com.apple.streamingkeydelivery の一つで、指定する形式のバージョンは 1 です。異なる鍵形式の同時宣言は拒否します。非ゼロの音声初期遅延も対象外です。

TS 出力で映像と音声がある場合は、それぞれ別の TS プレイリストと、それを関連付けるマスタープレイリストを作ります。一つの TS セグメント内に両方を多重化する出力は、現在の実装では作りません。

共通の対象外と上限

ローカル DASH は静的な一つの Period と、原本のディレクトリ内を参照する有限のテンプレート、リスト、単一ファイルの索引に対応します。テンプレートは公称時間または明示的な時系列を使い、リストはファイルまたは対応するバイト範囲を指定できます。単一ファイルの索引は階層を持たず、同じメディアファイルを参照するものに限ります。ライブ、動的 DASH、複数 Period、HLS のバイト範囲、不連続、階層を持つ DASH の索引や外部の索引、保持できないイベントやレンディション情報は対象外です。字幕トラックや任意のトラック選択も現在の変換対象に含みません。

汎用変換の上限は、作業用に保存するデータが一トラックあたり 16 GiB、トラック数が 64、DASH の参照セグメント数が 100,000 個です。このほか、初期化メタデータや断片ごとの上限があり、利用可能な CPU とメモリに応じても処理を制限します。上限を超えた部分を無視して成功とすることはありません。

4. 導入と依存ツール

English

5. 鍵設定と秘密情報の扱い

English

入力鍵と出力鍵の役割

convert と verify は --keys-file で指定した JSON ファイルから鍵を読み込みます。ファイルには所有者だけがアクセスできる権限が必要です。環境変数から自動的に鍵を補うことはありません。入力鍵は原本の復号に、出力鍵は結果の暗号化と検証に使います。同じ暗号方式への変換でも、入力鍵と出力鍵は独立しています。

analyze と plan --save も、原本の確認に入力鍵が必要な場合は同じ --keys-file を使えます。計画を保存する段階では出力鍵は不要です。convert --plan と verify --plan に、実行時の鍵を別途渡します。

鍵は 16 バイトを 32 桁の十六進数で表します。KID は key identifier、つまり鍵を選ぶための識別子で、暗号鍵そのものではありません。IV は initialization vector、暗号化の開始状態を指定する値です。KID やメディア内の IV は公開メタデータになる場合があります。

macOS/Linux では、まず所有者だけがアクセスできるディレクトリを作成します。その中にエディターや秘密情報の管理ツールで設定ファイルを作ってください。次の例では後述の構造例を keys.json に保存した後、ファイルの権限も設定します。

6. メタデータの確認と plan

English

鍵を使わずに宣言情報を確認する

analyze --metadata-only は MP4 のメタデータや DASH/HLS の宣言を読み取ります。鍵、デコーダー、Shaka Packager は不要です。入力形式は内容から判定します。JSON は schema_version: 1 を持ち、形式、トラック・サンプル記述ごとの保護方式、既知の KID、DRM システム名、findings の説明トークンなどを返します。鍵、IV、ライセンス URL、鍵 URL は含めません。

MP4 では構造情報を読み、メディアのデータ全体は走査しません。DASH/HLS では宣言情報を読みます。いずれも media_verified: false であり、全サンプルの復号・デコードや再生を確認するものではありません。未対応または不完全な暗号情報は unknown のままです。HLS の SAMPLE-AES 宣言だけで MP4 の暗号方式を断定することはありません。

ローカル HLS の子プレイリストは入力ディレクトリ配下の参照だけをたどります。リモート、欠落、循環、ツリー外参照は解決しません。URL の HLS では宣言と必要な子プレイリスト、DASH では MPD を取得します。初期化ファイル、セグメント、鍵、ライセンスは取得しません。

URL の MP4 は HTTP の Range リクエストで必要な位置だけを読みます。応答の範囲を確認し、box（MP4 を構成するデータの単位）の見出しと、再生構造を記録した moov を取得します。moov がファイル末尾にあっても、映像・音声のデータを格納する mdat は読み飛ばします。Range 指定を無視する配信元では、ファイル全体を取得せず拒否します。

URL のメタデータは非公開の一時データとして扱い、保存計画やオフライン変換の原本にはしません。--download-dir は不要です。ライブ HLS や dynamic DASH の宣言も読める場合がありますが、更新を追い続けたり、VOD が完結していることや変換可能なことを確認したりする機能ではありません。原本全体の取得と検査には、第8章の通常の URL 解析を使います。

HLS のマスタープレイリストは画質や音声などの選択肢を列挙し、それぞれのメディアプレイリストを参照します（RFC 8216 第4.3.4.2節）。ローカル・URL のどちらでも、参照先が別のマスタープレイリストだった場合は、その先をたどらず hls-nested-master-playlist で拒否します。参照を何段もたどることで解析結果が増幅し、メモリを過剰に使うことも防ぎます。

--metadata-only と --download-dir、--keys-file、--packager-bin、--max-workers、--measure は併用できません。URL には第8章の --fetch-policy を指定できますが、ローカル入力には指定できません。メタデータ解析と取得ポリシーの両方の上限を適用します。解析の主な上限は一マニフェスト 4 MiB、合計 16 MiB、32 プレイリスト、128 参照、トラックごとに 64 KID、MP4 の moov 情報 16 MiB です。MP4 はローカル入力・URL 入力とも、入れ子を含む解析対象の box を 16,384 個までに制限します。小さな box が多数あると、データ量以上に解析用メモリが必要になるためです。上限に達した後は新たな box の管理領域を確保せず、mp4-box-count-limit で拒否します。

プレリリース中の CLI 整理に伴い、従来の inspect INPUT は削除しました。analyze --metadata-only INPUT に置き換えてください。旧名の別名コマンドは残していません。移行の説明（英語）も確認してください。

analyze による入力データ全体の確認

--metadata-only を付けない analyze は、変換と同じ処理エンジンで原本全体を読み、全サンプルの符号化データ、コーデック設定、時刻、対応する再生範囲を Rust で確認します。--decode を付けると、原本全体のデコードも必須になります。input_admitted: true は、確認した入力が対応条件を満たしていることを示します。出力形式の候補が表示されても、指定する暗号方式との組み合わせは計画時に確認します。変換結果や DRM 再生の動作確認を済ませたという意味ではありません。ローカル MP4・DASH・HLS が対象です。URL 入力の保存手順は第8章に示します。

入力の確認では同じトラック一式を複製して照合する処理を省き、各トラックを直接検査します。MPEG-TS では全パケットの内容と時刻を読み、元の TS パケットから得た証拠との一致、対応する AVC の全スライスヘッダーと時刻設定を確認します。--decode はコンテンツ全体のデコードを追加します。プレイリストが参照する画質別の映像と音声はすべて対象です。別コマンドの verify では引き続き原本と出力をそれぞれ読み取って比較します。入力確認の結果を使って、後のコマンドの再検査を省くことはありません。

入力に互換処理を適用した場合は、compatibility_notes に固定の識別コードを示します。例えば、実データを含まない TS のパディングや、実際の区間を持たない隣接した HLS の広告境界タグが対象です。原本のバイト列は保持し、メディア内容と時刻の検査も行います。受理する条件と処理方法は、TS の互換処理の説明（英語）に記載しています。

plan による変換条件の確認と保存

--save を付けない plan INPUT は入力の宣言情報を使って変換先の候補と必要な条件を確認するモードです。--to は必須で、--format を省略すると入力形式を引き継ぎます。このモードではカンマで区切って指定した形式をそれぞれ変換候補として示します。複数の出力を実際にまとめて作るには、後述の --outputs を使います。

compatible は宣言と指定の組み合わせが整い、すべての要求形式に候補経路があることを表します。execution_available には、出力形式が一つであることも必要です。複数形式の計画は成功しても execution_available: false になり得ます。

どちらも、入力データが対応条件を満たすこと、鍵が正しいこと、必要なツールがあること、実行時の処理方法が決まったことまでは保証しません。source-profile-validation-required などの条件は実行時に確認します。SAMPLE-AES の宣言が正しくても、実際の TS 構成や IV の検証は必要です。このメタデータ確認用の JSON を、実行用の計画ファイルとして convert --plan に渡すことはできません。

details がある場合は、宣言された暗号、暗号化単位、パターン、未確定の範囲を示します。変換成功レポートの processing は実際に選んだ経路です。計画の候補と区別してください。

単一出力の実行用計画は新規の出力先と --save を指定して保存します。原本全体を確認し、解決後の出力形式を一つ記録します。

計画にはローカルのプレイリスト・メディア、それぞれのサイズと SHA-256 ハッシュ、出力形式・暗号方式、出力先の絶対パスを記録します。SHA-256 は内容の変更を確認する値です。パスは保存時のマシンと配置に依存するため、計画は所有者専用にし、原本・出力のディレクトリ外へ保管してください。未対応のバージョン、不明なフィールド、計画 ID の不整合、原本の変更、安全でない保存先は拒否します。ID は整合性の確認用であり、第三者の署名や実行許可ではありません。

新しい単一出力計画は schema 9、名前付き出力計画は schema 10 です。処理方式、境界の扱い、出力パスとセグメント名、DASH の参照形式、required_depth を計画の ID に含めます。検査の最低条件は既定で native、plan --save --decode で decoded になり、後の convert --decode・verify --decode で強められます。下げることはできません。version 1〜8 は保存済みの設定を使い、7・8 はトラックの接頭辞も維持します。1・2 は完全デコード、3・4 は保存済みの検査水準と結合処理を引き継ぎます。

鍵、署名付き入力 URL、認証ヘッダー、ライセンス URL、HLS 鍵 URI、実行プログラムの引数は計画に保存しません。鍵は実行・検証時に --keys-file で渡します。version 1・3・5・7・9 の単一出力計画では、DRM シグナリングの選択も実行時の設定です。version 2・4・6・8・10 では DRM システムの選択とマニフェスト検証方針を計画に固定し、鍵やアドレスは引き続き別の設定で渡します。verify --plan は原本のハッシュと実際の出力の形式・暗号方式を照合し、原本と結果のコンテンツ全体および時刻が一致するか確認します。ライセンス取得や実機再生は別途検証が必要です。

Unix 系では、出力と計画の親ディレクトリは、自分が所有し、他のユーザーが書き換えられない信頼できる場所を使ってください。保存する計画の出力先が安全でない場合は、メディアの確認に入る前に拒否します。共有一時ディレクトリを扱う条件と削除時の制約は、作業領域の権限の説明（英語）に記載しています。

計画保存では変換結果を作りません。暗号化された原本の確認には入力鍵を使った復号を伴う場合があり、実行時にも原本の条件を再確認します。

ディレクトリの保持と DASH の参照形式

取得時は video/1080p/ などのメディアと子プレイリストのパスを保持します。input.m3u8・input.mpd は、保存先を参照するよう書き換えたマニフェストです。raw/ には取得時のマニフェスト原文と、URL・サイズ・ハッシュを記録した非公開の raw/index.json を残します。メディアは一度だけ保存し、raw/ に複製しません。URL を含むため非公開で原本と一緒に保管してください。鍵はダウンロードしません。

出力も同じディレクトリに置き、マニフェストは master.m3u8・manifest.mpd です。メディアのディレクトリが別々なら接頭辞は付けず、r000600.ts は fMP4 では init.mp4 と r000600.m4s、HLS TS では .ts のまま出力します。同じディレクトリへ別ファイルとして出すトラック（映像・音声）は、元のプレイリスト名と種類に基づく接頭辞で区別します。対応する連番の開始位置とゼロ埋めは保持し、結合後の分割数に合わせて必要な数の名前を付けます。元の区切り位置は保証しません。HLS と DASH の list は、分割数が同じ場合だけ任意名の拡張子以外の部分を保持し、分割数が変わる場合は seg_1 から命名します。DASH のテンプレートでは対応する連番の規則（名前の1か所の数字が1ずつ増える形）に合わない名前を seg_1.m4s に替えます。任意名を残すには --dash-addressing list を指定します。MP4 入力には元のセグメント名がないため、元のディレクトリ内に seg_1 から作ります。

一つのレンディション（画質や音声別の配信単位）には同じ親ディレクトリが必要です。安全でないパス、名前の衝突、原本の外への参照は拒否し、追加 origin には取得設定の許可が必要です。以前の取得データは既存のローカルパス、保存計画は記録済みの配置を使います。取得元の構造にする場合は新しいディレクトリへ取得し直してください。ディレクトリの詳しい条件（英語）。

主な追加設定は max_playlist_bytes、max_playlists、max_segments_per_track、max_resource_bytes、max_total_resources、min_free_disk_bytes、timeout、attempts です。数値の型と範囲を確認し、不明なフィールドや重複したフィールドは拒否します。connections は同時取得数の上限です。利用可能な CPU・メモリと --max-workers によっては、実際の同時取得数がそれより少なくなる場合があります。

max_playlist_bytes は HLS プレイリストだけでなく DASH MPD 一つあたりの上限にも使います。MP4 やメディアリソース一つあたりの上限は max_resource_bytes、取得全体の上限は max_total_bytes で指定します。

取得処理の実装上の上限は、HLS プレイリストまたは DASH マニフェスト一つあたり 4 MiB、マニフェストとメディアの合計リソース数が 100,000、取得計画に使うテキストと URL メタデータが 16 MiB です。リソース本体は所有者だけがアクセスできるファイルに逐次保存します。取得ポリシーを緩めても、メディアの対応条件や上限は変わりません。

成功 JSON の download には保存先の表示パス、エントリーポイントと相対パス、retained: true が入ります。入力 URL とリクエストヘッダーは含めません。一方、保存した原本には署名 URL などが残り得るため、保存先を保護してください。

AAC と二秒セグメント

一般的な AAC-LC フレームは 1,024 サンプルです。48,000 サンプル/秒では約 21.333 ミリ秒になり、二秒は 93.75 フレームです。44,100 サンプル/秒では約 23.220 ミリ秒で、二秒は約 86.133 フレームです。フレームの途中で符号化データを切れないため、音声の境界や個数は二秒の映像セグメントと一致しないことがあります。

音声のサンプルレートと、ファイルに時刻を記録する単位は別のものです。TS の時刻は一秒を 90,000 等分した整数で記録します。AAC の一フレームは 48 kHz なら 1,920 刻みちょうどですが、44.1 kHz では約 2,089.796 刻みになるため丸めが必要です。毎回 2,089 だけ加えると、処理する時間が長いほどずれが大きくなります。

drmr は原本の PES（符号化した映像や音声をまとめたパケット）にある時刻を保持し、その中の各 AAC フレームの時刻を実際のサンプルレートから求めます。原本を受け入れる際は、パケット先頭の時刻を整数に丸める処理と、パケット内の各フレームの時刻を求める処理を分けて検査します。トラック全体に共通の時刻の基準を使い、丸め方が一貫していることを確認します。確認できた各フレームの時刻は、出力との比較で一つずつ厳密に照合します。音声トラックを一つだけ格納した fMP4 を使う HLS・DASH にも同じ規則を使います。対象は AAC-LC・44.1 kHz、時刻の単位は 90 kHz です。出力との時刻照合に誤差は認めません。

44.1 kHz の AAC を分離するときは、作業用 fMP4 の時刻も 90 kHz のままにします。一方、デコーダーに渡す設定には本来の音声レートである 44,100 サンプル/秒とチャンネル構成を記録します。AAC の符号化データ、フレーム数、元の表示時刻とデコード時刻は保持し、--decode ではデコードした全サンプルも照合します。このトラックから Shaka Packager で HLS・DASH・TS の出力を作ります。作業用 fMP4 は最大 128 フレーム（符号化データで最大約 1 MiB）ずつ書き出すため、コンテンツ全体をメモリに保持する必要はありません。

FFprobe が TS の一フレームの継続時間を 2,089 刻みと表示していても、次の復号時刻までは 2,090 刻み離れていることがあります。MP4 のサンプル継続時間にはこの実際の時刻差を記録します。次の時刻がない最終フレームだけは、TS の整数の継続時間を使います。検証では MP4 の継続時間が次の復号時刻につながること、原本の全 PTS・DTS と最終的な終端が一致することを確認します。原本の時刻の丸めを理由に、変換結果の時刻ずれを許すことはありません。詳細は AAC のサンプルレートと時刻の説明（英語）を参照してください。

44.1 kHz の入力プレイリストでは、最終区間以外の EXTINF が「この区間の先頭フレームから次区間の先頭フレームまで」を表す場合もあります。最終フレーム全体を再生する区間では、音声サンプル数から求めた長さ、または最終フレームを 2,089 か 2,090 刻みとして求めた長さとの一致を確認します。こうした記載方式に応じて原本の区間長を検査しますが、PTS・DTS の比較に許容差を設けるものではありません。

最後のフレームの一部だけを再生する指定は、時刻の丸めとは別に扱います。符号化データと各フレームの正確なサンプル範囲は残し、どこまで再生するかを別途記録します。fMP4 HLS・DASH では MP4 の二つの編集項目で原本の開始時刻と正確な再生時間を保持します。全体の時刻単位には音声一サンプルと TS 一刻みの両方を正確に表せる値を使い、メディアの時刻は 90 kHz のままにします。編集項目はパッケージング後に追加します。全フレームの検査や再変換には、この形式と確認できた編集だけを除いた作業用コピーを使います。再生範囲は検査したフレーム数・時刻と照合し、原本と最終出力の編集は残します。再変換時にはパッケージャーによる時刻調整の丸めも避けられます。

HLS の区間長は出力自身の再生範囲から求めます。DASH は符号化されたセグメントの時刻表を保持し、映像・音声それぞれの再生終端をすべて含むように全体の長さを決めます。TS 出力では最終プレイリストに短縮後の長さを記録します。独立検証は出力自身から再生範囲を読み直し、原本の全データと実際に再生する音声サンプルの両方を照合します。MP4 に記録された音量、再生速度、トラックの有効・無効も検査します。この処理では標準の音量と速度、有効なトラックを前提とし、符号化データが同じでも再生設定を変えた出力は検証を通しません。詳しくは AAC の再生終端の説明（英語）を参照してください。

44.1 kHz の音声では六秒が約 258.4 AAC フレームに当たります。フレーム全体を保持すると、258 フレームの区間は約 5.990748299 秒、259 フレームの区間は約 6.013968254 秒になります。drmr はこの長さを六秒に丸めたり、フレームを切り落としたりしません。segments は元の区間と長さの記載を保持し、stitch は別のフレーム境界で分割することがあります。

整数の EXT-X-TARGETDURATION は各区間の長さを最も近い整数に丸めた値以上である必要があります。原本の六秒という上限を引き継ぐ場合、6.013…秒の区間もこの条件に収まります。drmr は最終的な区間長の記載を厳密に調べ、映像と音声の全メディアプレイリストに原本の共通上限を設定します。マスタープレイリストの帯域宣言もその上限と実際の出力サイズで再計算します。このヘッダーの補正で原本や EXTINF の長さは変更しません。HLS の上限を引き継がない MP4・DASH 入力や以前の計画では、生成された余裕のある上限を使います。独立検証でも最終ファイルのセグメント長と上限を照合します。RFC 8216 には VOD の字幕と I-frame プレイリストに関する別の例外がありますが、通常の映像・音声の上限は揃える必要があります。

この差は音声の欠落・重複・すき間・重なり・累積ずれを許す理由にはなりません。「一フレーム以内なら同じ」という許容差は使わず、すべてのパケット時刻と全サンプルを確認します。

48 kHz の十秒の試験 MP4 は 470 AAC フレームを含み、すべてをデコードすると一チャンネルあたり 481,280 サンプルになります。先頭の初期遅延 1,024 サンプルと末尾の 256 サンプルを除くため、実際の再生範囲は一チャンネルあたり 480,000 サンプルです。TS への変換でパディングも再生される構成になっている場合は、その TS 自体の再生範囲を基準にします。元の MP4 に合わせて短くすることはありません。

有限再生範囲を別に照合する理由

圧縮パケットが同じでも、MP4 の編集情報が消えると、再生すべきでない先頭や末尾が聞こえる場合があります。FFmpeg 9.0.2 の一部のフラグメント化 MP4 読み取りでは、有限の末尾切り詰めが通常デコードに反映されません。このため、単に同じツールで普通に復号して比較するだけでは足りません。

--decode を付けた有限 AAC の処理では、編集情報の自動適用やサンプルの破棄をせずに原本と結果をすべてデコードし、内容と個数を比較します。その後、各ファイルの情報から確認した開始位置と長さを一度だけ適用し、再生される内容と個数も比較します。さらに、プログレッシブ MP4 原本を通常どおりデコードした結果が、原本自身の再生範囲と一致することも確認します。変換結果に合わせて原本を切り詰めることはありません。

比較にはデコーダーの 32 ビット浮動小数点出力を使い、16 ビット整数への変換で生じる追加の丸めを避けます。ハッシュの計算と再生範囲の選択は固定サイズのバッファで逐次処理するため、非圧縮音声全体をメモリに保持する必要はありません。ファイル内の再生設定、音量、速度、有効フラグ、映像の表示寸法も確認します。ただし、すべてのプレーヤーで同じ編集情報が適用されることを保証するものではありません。

マニフェストに記載する時刻の照合

TS の時刻はゼロ以外から始まることが多く、音声が最初の映像より先に始まる場合もあります。TS→DASH では原本の全トラックの中で最も早い表示時刻を共通の始点にします。DASH の presentation-time offset を使って配信時刻に対応させ、トラックごとに個別にゼロへずらすことはしません。

パケットとセグメントの時刻は整数や有理数で正確に扱います。TS→DASH の最終 Period や、有限再生範囲を持つ DASH/HLS の再生時間を小数文字列で記載する際は、正確な終端を小数九桁で切り上げます。差は 1 ナノ秒未満です。これはマニフェストへの記載方法の規則であり、パケット時刻に誤差を認めるものではありません。記載された値がこの計算結果と異なれば拒否します。

MP4 の編集情報には、符号化されたサンプルの時刻を実際の再生時刻へ対応させる補正値が含まれることがあります。fMP4 で編集区間の長さを 0 とする指定は、それ以降のメディア全体に補正を適用します。再生範囲が空とは限りません。drmr は対応する映像・音声の編集情報を適用して DASH の区間、全体の長さ、索引を検査し、元のパケット時刻も別途照合します。W3C の初期化セグメントの規定（英語）。

有限編集を持たない通常の HLS では、EXTINF の小数表現に別の丸め規則を使います。その幅はメディアクロックの一刻みと約一ミリ秒のうち大きい方です。この規則でも、全パケットの時刻は厳密に比較します。有限音声の一サンプルの違いを、この丸め幅を理由に受け入れることはありません。

signaling指定した DRM 情報が、実行設定および実際のメディアとマニフェストの宣言に一致するか
conformance必須の外部マニフェスト検査の結果、または検査を要求していないこと

PSSH、PlayReady 情報、KID、FairPlay の宣言が変われば、復号そのものができても検証は失敗し得ます。drms が空の場合はサービス固有の DRM 情報を要求しておらず、シグナリングを検証済みとは表示しません。この場合もメディア全体と暗号方式の確認は必要です。

サービス固有の DRM を指定しない cenc / cbcs 出力にも、W3C の Common SystemID を使う PSSH が含まれることがあります。これは鍵の識別子を伝えるための情報であり、コンテンツキーそのものやサービス固有のポリシーは含みません。drmr は、自身が生成する「KID が一つでデータ部がない形式」を出力設定と実際のトラックの保護情報に照らして検査します。この検査で DRM サービスやライセンスの動作を確認できるわけではなく、入力の対応範囲も変わりません。

共通の HLS/DASH 変換とコンテンツ全体の検証では、Rust で実装した内蔵 Linter が最終マニフェストを検査します。この検査に外部ツールは不要です。Linter は文法や宣言の整合性を規則に沿って調べる仕組みです。HLS では文法、セグメントと鍵の状態、必要なプロトコルバージョン、関連プレイリストの参照を検査します。Apple 固有の VOD 規則は基本の HLS 規則と区別しています。DASH では対象とする静的配信プロファイルの構造、継承、参照方式、タイムライン、保護情報の宣言を検査します。独自の Rust 実装であり、XML スキーマや Schematron 全体を実行するものではありません。

結果には規則ごとの成功・失敗・未検査と仕様の参照先を記録します。検査範囲内の未対応機能、参照先プレイリストの不足、資源上限への到達、診断の打ち切りがあれば、合格とは判定しません。メディアの実測や配信環境が必要な規則はマニフェストだけの検査の対象外とし、コンテンツ全体の検証結果とは分けて示します。診断には規則 ID と原文中の位置を示しますが、マニフェスト本文、鍵 URI、保護情報のペイロードは転記しません。小さい入力は一つの処理として実行し、大きな独立した文書は CPU とメモリの制約内で並列に処理できます。

conformance: "required" を指定した出力では、HLS は Apple の mediastreamvalidator をプレイリスト検査モードで使います。DASH はローカルの DASH-IF Conformance Software による XML スキーマと Schematron の検査を使います。XML スキーマは MPD の構造、Schematron は追加の記述規則を確認する仕組みです。HLS の参照先の子プレイリストを含め、暗号化された最終出力のマニフェストを検査します。

外部検査はメディア全体の内部検証とは別に行います。暗号化メディア全体の規格適合、ライセンス取得、実機再生を確認するものではありません。必要なツールがない場合、検査が中断した場合、結果が不完全な場合、検査エラーがあった場合はいずれも失敗です。"none" は外部検査を要求しない指定であり、検査に成功した場合とは区別して表示します。

Apple の HLS ツールは macOS の環境に準備します。DASH は対応するローカルの DASH-IF ソフトウェアと依存ツールを用意し、DRMR_DASH_IF_ROOT にその配置先を設定します。--hls-validator-bin は Apple の実行ファイルを選び、既定値は mediastreamvalidator です。--dash-validator-bin はローカル DASH-IF アダプターを実行する PHP の場所で、既定値は php です。任意の DASH 検査プログラムを渡すオプションではありません。実行ファイルの場所は計画に保存しません。詳細はマニフェスト検証の準備と範囲（英語）を参照してください。

English

並列数の自動調整と --max-workers

通常の analyze、plan --save、convert、verify は、利用可能な CPU とメモリ、映像の寸法、リソースのサイズ、トラック数から並列数を自動で調整します。--max-workers には 1 から 64 の範囲で上限を指定できますが、実際にはそれより少ないワーカーを使う場合があります。省略時に選ぶ推奨数は最大 32 です。analyze --metadata-only とは併用できません。

ワーカー数を変えても、内容と時刻の検証は省略しません。トラック処理、セグメント処理、原本解析では、同じプロセス内で外部処理に使う CPU・メモリの予約枠を共有します。別々の CLI プロセス間では予約枠を共有しません。

通常の analyze はダウンロード後も続きます。原本のコピーを照合してトラックを準備し、全サンプルの符号化データ、設定、時刻、再生範囲を Rust で検査するためです。--decode では、デコードした映像・音声全体も確認します。並列に動かせるのは各段階の独立した作業で、すべての処理や外部ツールの呼び出しが同時に動くわけではありません。回線やディスクの速度、プロセスの起動、トラック数、順序を保つ必要のある検査も所要時間に影響します。性能を比べる場合は、保存済みの同じローカル原本を使い、並列数一つの場合と自動選択の場合を比較してください。概要だけを知りたい場合は analyze --metadata-only を使えますが、変換できるかどうかの確認にはなりません。

TS の準備では独立したセグメントのメタデータと符号化フレームを並列に読み取ります。メモリに保持するのは、件数を制限した小さな解析結果です。その後、プレイリストの順序で再生時間と時刻の境界を照合し、メディアプレイリストを一つずつ処理します。原本に対する全サンプルの検査は引き続き必要で、--decode の場合はトラック全体もデコードします。

内蔵のマニフェスト検査も同じ予約枠を使います。小さい入力は呼び出し元で処理します。大きな HLS は文書ごとに、大きな DASH は一度解析したツリー内の独立した検査ごとに並列処理できます。処理用のプールを入れ子にせず、子プレイリストの解析結果や継承したタイムラインを再利用します。マニフェストの保持と検査に必要なメモリを予約し、ファイルの識別情報と内容も照合します。バイト数、ノード数、参照数、診断数などの上限に達した場合は不完全な検査として報告し、合格にはしません。

資源見積もりの範囲

Linux では読み取り可能な CPU quota、メモリの cgroup 上限、親 cgroup の上限も見積もりに使います。cgroup は、コンテナやサービスが使う OS の資源を制御する仕組みです。資源情報を取得できない場合は、512 MiB の枠で子処理を一つ実行する前提で見積もります。一つの処理もこの枠に収まらないと判断した場合は、resource-budget で失敗します。

利用可能なメモリがわかる場合は、その四分の一を基準に、最低 256 MiB の予約枠を確保します。トラックごとの保持データも見積もりに含めます。子処理については基本の使用量に加え、画素数、入力の処理量、取得する出力の上限を考慮します。これは処理を開始できるかを判断するための見積もりであり、OS によるメモリ制限や最大使用量の保証ではありません。

追加のデコードを行う場合、FFmpeg のデコーダー・エンコーダー・フィルターと FFprobe のデコードには、それぞれスレッド数 1 を設定します。補助スレッドも含めて一つになるわけではありません。音声ハッシュの計算とパケット時刻の照合は逐次処理します。ただし、トラックやセグメントのメタデータは保持するため、メモリ使用量全体が常に一定になるわけではありません。

外部処理から取得する標準出力の上限は既定で 16 MiB、標準エラーは 1 MiB です。上限を超えた場合は output-limit などで失敗し、途中で切れたデータを使って検証を成功とすることはありません。待機中も制限時間と停止要求を確認します。

Ctrl+C と終了確認

macOS/Linux の汎用 convert・verify は SIGINT、SIGTERM、Windows は Ctrl+C と Ctrl+Break で協調停止します。予約待ちと新規処理を止め、所有する子プロセスを終了し、後片付けを確認します。公開前に停止要求を観測した場合は結果を配置しません。

終了コード 130 は処理の停止と子プロセスの終了確認が完了したことを示します。cleanup-unconfirmed や media-cleanup-unconfirmed は、停止要求による終了であっても失敗として扱います。強制 kill や OS による強制終了では協調停止の処理を行えず、一時領域が残ることがあります。

Unix では drmr が作成したプロセスグループで、Windows では job object で子孫プロセスを管理します。終了要求を送っただけでは、子孫プロセスがファイルを閉じたと判断しません。Unix で直接の子プロセスが終了した後のグループ確認と、Windows で job の終了通知を待つ処理には、それぞれ別の 30 秒の制限時間があります。ただし、ファイル I/O、名前解決、OS のスケジューリングも含めた全体の終了時刻を厳密に保証するものではありません。

計測値の読み方

過去の完全デコードを伴う計測は、現在の --decode に相当する処理範囲の記録です。現在のビルドで Rust の標準検査を計測した値ではありません。性能は検査範囲を揃えて比較してください。

--measure は --json と併用します。メディア検証の条件は変えず、数値を追加します。各処理段階は重なったり入れ子になったりするため、その時間を単純に合計して全体の時間とみなさないでください。

短い十秒アセットの時間は起動処理やキャッシュの影響を受けます。メモリのサンプリング値は真の最大値ではありません。比較する場合は、原本・ツールのバージョン・ビルド設定・ワーカー上限・ホスト負荷を揃え、まず同じ完全検証が通ることを確認してください。

内蔵ライブラリの検査速度を測るため、ソース c1458e7d を Rust 1.99 の release ビルドで実行しました。環境は論理 CPU 10 個、メモリ 32 GiB の macOS ARM64 です。2026年10月21日の測定では、マスタープレイリストと、各1000セグメントのメディアプレイリスト64本を検査する時間が、逐次処理で 14.50 ms、自動選択された10ワーカーで 3.37 ms でした。どちらの検査レポートも一致しました。小さい入力は1ワーカーで処理します。

30000項目の DASH タイムラインでは逐次処理が 5.22 ms、自動選択が 5.27 ms となり、並列化で速くならない入力もありました。これらは実行順を変えて三回測った中央値で、変換時間ではなくライブラリによる検査全体の時間です。測定には作成した検査用データを使いました。同時に実行していた本プロジェクトのメディア試験は停止しましたが、ホスト上の他の処理までは分離していません。追加のメモリ確保量とプロセスのメモリ使用量は別々に測定しており、詳細はリンク先に記載しています。

Docker の Web コンソール

Docker Desktop では追加の host networking 機能が必要です。コンテナ内の loopback だけで待ち受けるサーバーには、通常のポート公開だけでは接続できません。接続のために loopback・Host・Origin の保護を解除しないでください。ネイティブの Desktop GUI は、このイメージには含まれません。

Windows では Docker Desktop の WSL 2 連携を使い、Linux シェルで実行します。秘密情報を含む設定は Linux 側のファイルシステムに置いてください。Windows ドライブをマウントした場合は権限の扱いが異なるため、ネイティブ Windows 向けの ACL の設定手順は適用できません。

イメージ内の /usr/share/drmr/build-manifest.json は元コミット、ツリー、依存関係の実際のバージョンを記録します。ライセンスは /usr/share/drmr/licenses、対応するメディアツール等のソースは /usr/share/drmr/sources にあります。Debian パッケージ全体のソースミラーではありません。

13. ローカル Web コンソール

English

起動と対象

Web コンソールは認証なしのローカル操作画面です。信頼できるマシン上の loopback で使い、リバースプロキシやポート転送で公開しないでください。Host と Origin の確認は他のローカルプロセスを認証する機能ではありません。

http://127.0.0.1:8080 を開きます。二つのルートディレクトリが必要です。DRMR_BIND_PORT でポート、DRMR_MAX_WORKERS で保存計画の各処理に使うワーカー数の上限を設定します。自動割当てでもこの上限を超えません。メディアと保存計画は、許可された入力フォルダーから選びます。

サーバーとジョブ用の CLI は同じバージョンを使います。--cli で差し替える場合は実行ファイルを直接指定してください。別の CLI を起動するラッパーを指定すると、子プロセスを管理するための起動条件を満たさず、拒否される場合があります。

鍵や取得設定を使う場合は、起動前に DRMR_COMMON_CONFIG_ROOT へ非公開の設定フォルダーを指定します。入力、出力、独自の静的ファイル配信先と重ならないフォルダーを使ってください。

非公開の設定を選ぶ画面では、ファイル名とフォルダー名を番号に置き換えて表示します。各ページの並びはファイル名順です。選択するファイルはローカルのフォルダーで確認してください。設定の内容と名前はコンソールに表示しません。

保存計画を使う変換

「新しい変換」ではCLI と同じ保存計画を使って次の操作を個別に実行します。

  1. 「ローカルメディア」「入力 URL」「CLI の保存計画」から入力を選び、「入力を開く」を押します。URL は第8章の対応条件を満たす MP4・static DASH・完結した HLS を指定できます。ファイルはサーバーまたは Desktop で許可したフォルダーから選びます。ブラウザーへのアップロードや、任意のホストパスの入力は行いません。
  2. 新しい入力では必要に応じて「鍵ファイル」と「並列処理数」を指定し、「解析する」を押します。URL の取得設定は「取得ポリシーファイル」で選びます。鍵と取得ポリシーは非公開の設定フォルダーに置き、内容を画面へ入力しません。
  3. 解析後、出力を 1〜8 件追加します。出力名、形式、暗号化方式、DRM 情報、外部マニフェスト検査を指定し、新しい出力の親フォルダーとフォルダー名を選んで「計画を保存」を押します。対応する入力条件と組み合わせは保存時に確認します。
  4. 「元の計画ファイルを取得」で計画を非公開に保管し、「変換する」を押します。出力済みの場所は上書きできません。出力の設定を編集した場合は、新しい計画を保存してください。
  5. 変換後は「改めて検証する」で、保存した計画と既存の出力を再変換せずに照合します。後日も「CLI の保存計画」から同じ計画を開けば、解析や変換を繰り返さずに検証できます。

新規のコンソール計画は出力が一つでも名前付き出力の v10 です。計画を保存する際に処理方式も選択します。DASH 出力には「DASH セグメントの参照」があり、CLI と同じ四つの形式を指定できます。「完全デコードも実行」は CLI の --decode と同じ指定です。チェックを外しても保存計画の最低条件は下がりません。結果は Rust 検査、実際のデコード、デコード未要求を分けて表示します。鍵ファイルを指定する場合、解析には v1・v2 のどちらも使えます。新規コンソール計画と名前付き出力の v2・v4・v6・v8・v10 計画には v2 の鍵ファイル、単一出力の v1・v3・v5・v7・v9 計画には v1 の鍵ファイルを使います。ファイルの書式は第17章の CLI リファレンスを参照してください。

取得した計画は元のバイト列と絶対パスを保持します。入力ファイルや出力先の情報が記録されているため、非公開で保管し、別環境へ移すためにパスを書き換えないでください。鍵や実行ファイルのパスを HTTP リクエストで渡す機能はありません。鍵ファイルの内容はブラウザーで取得しません。

URL の入力は送信時に消去し、以後は「入力 URL」とだけ表示します。認証情報がクエリだけでなくパスにも含まれる場合があるため、サーバーは送信された URL を画面へ返しません。

一つのセッションで受け付ける操作は最大 32 回です。上限に達したら計画を取得し、「この変換を閉じる」で終了してから保存計画を開き直すと、既存の出力を検証できます。開始結果が不明なときは「状態を確認」で同じ操作だけを照会します。実行中や後処理を確認できない間は閉じられず、画面や言語を切り替えても実行枠は解放しません。

ジョブの状態と停止

開始要求への応答が届かない場合は、同じ要求とジョブの状態を確認します。「状態を確認」は照会だけを行い、変換を再送しません。画面や言語を切り替えても、実行中の処理を管理する枠は解放しません。

「停止」はそのジョブと管理中のメディアツールの終了を要求します。応答だけで後片付けが完了したとは判断せず、最終状態とログを確認してください。終了を確認できない間は実行枠を保持し、新しい処理を開始しません。サーバー終了時も新規処理の受け付けを止め、管理中の処理が停止するまで待ちます。終了できない原因を解消してから再試行してください。強制終了では、この確認は行われません。

保存するファイルと秘密情報

取得した原本、保存計画、結果、ログはディスクに残ります。画面を閉じても消去されず、実行中の処理が停止したと判断することもできません。これらの保存先は非公開にしてください。入力 URL は送信後に画面から消去し、鍵や取得ポリシーのファイル内容はブラウザーへ送りません。

15. 結果・終了コード・問題の切り分け

English

JSON の結果

スクリプトから読む場合は --json を使います。メディア検査の report schema 2 は、最低検査範囲、入力確認か原本と結果の比較か、三つの Rust 検査、実際に得たデコードの証拠を分けて記録します。例えば既定の比較結果は次の形式です。--measure には --json も必要です。

passed は必要な検査範囲を満たしたという意味です。not-checked はデコード内容の一致を表しません。--decode による入力確認は scope: "source-admission" と status: "source-decoded"、原本と結果のデコード比較は status: "content-compared" と実際の equal を記録します。入力解析の schema 2 では verification にこの情報を含めます。旧 media_verified・decoded_content_equal は新しいメディアレポートには出力しません。旧 schema 1 のレポートは完全デコード済みという従来の意味を保持します。メタデータのみ・マニフェストのみのレポートは別のスキーマです。

残り時間は今回の実行で得た工程ごとの速度から見積もります。並列の出力では最も時間がかかる出力と後続の検査を考慮し、ファイルの整合性を確認する処理も見積もりに含めます。以前の実行記録やコンテンツごとの固定時間は使いません。必要な工程の速度がまだ分からない間は残り時間を数値で出さず、estimating remaining time と表示します。処理中の作業だけの残り時間は先に表示できる場合があります。工程や負荷の変化で見積もりも変動します。--decode、必須の外部検査、それ以外の変換では全体の残り時間を推測しません。

ダウンロードの総数が決まると完了件数と進捗率を表示できます。TS の準備では現在のメディアプレイリストの全セグメントを数えます。各作業の残り時間は総数の確定から一秒以上経過して二件以上完了した後に見積もります。全 TS セグメントを読んだ後は、進捗率と残り時間を checking segment boundaries に替え、プレイリスト順に境界を検査します。

調査中など総数が不明な作業は作業名と経過時間を表示します。単一 MP4 の URL 取得では受信量だけを表示し、終了後の件数は 1/1 です。取得中の進捗率や残り時間はありません。取得の総件数は完了した調査リクエストと重複を除いたメディアを含み、受信量は再試行分も含むため保存サイズと異なる場合があります。並列数の上限は独立した作業に適用し、全工程が同じ並列数で動くわけではありません。

--progress json は作業名・件数・処理区間に加え、複数出力の pipeline に工程・出力別状態と取得できた概算を記録します。処理区間は重なったり失敗で終わったりするため、終了だけでは成功と判断できません。ヘルプやバージョンは進捗を出さず、--measure は別の計測で所要時間が重なる場合があります。

convert は原本と結果を比較し、対象のマニフェストと指定された DRM 宣言も Rust で検査します。結果には実施した検査を示し、外部検査は指定時だけ表示します。独立した verify は保存済みファイルを読み直して検査します。

進捗には URL、鍵、認証ヘッダー、入力・出力やツールのパス、生のメタデータや外部ツールの出力を含めません。引数の解析後は明示的な --progress json で標準エラーを JSON Lines にし、失敗・停止にも固定のエラーコードを付けます。引数の構文エラーや serve の起動エラー・接続先通知は別のテキストになる場合があります。成功は最後の結果と終了コードで確認してください。

FILE・PATH に指定するもの

FILE や PATH はファイルのパスを表す仮の名前です。使うファイルのパスに置き換えます。相対パスはコマンドを実行するディレクトリを基準にします。パスに空白がある場合は引用符で囲んでください。JSON の中身をオプションの直後に直接書く方式ではありません。

同じ FILE 表記でも、設定 JSON、生成済みの計画、実行プログラムでは渡すものが異なります。代表的な指定例と、内容の説明は次のとおりです。

通常の analyze はどちらのバージョンの鍵 JSON からも入力鍵を読み込めます。出力設定がある場合も、解析には入力鍵だけを使います。--metadata-only では鍵ファイルを指定できません。

--packager-bin の既定値 packager は起動環境の PATH から実行ファイルを探す指定です。別の場所に配置した場合は、その実行ファイルのパスを渡します。例えば macOS/Linux では次のように指定します。入力ファイル、出力先、鍵設定、実行ファイルの場所は自身の環境に合わせて置き換えてください。

Windows では例えば --packager-bin 'C:\media-tools\packager.exe' と指定します。実行ファイル自体のパスを指定してください。オプションの値にシェルコマンド全体や追加引数は含めません。CLI アーカイブには Shaka Packager は同梱されていません。

NEW_FILE・NEW_PATH・NEW_DIR は、これから作る保存先です。読み込む FILE とは異なり、既存の出力先を上書きするための指定ではありません。秘密情報を含むファイルは、鍵設定の保護手順に従って作成してください。

verify は検証用のコマンドです。target や format を指定して変換結果を作り直すことはできません。

単一出力の計画検証では plan_id、source_unchanged、output_matches_plan を返し、コンテンツ全体の比較結果を verification の下に入れます。成功には source_unchanged、output_matches_plan、verification.passed がすべて true である必要があります。PlayReady 情報を明示した場合は、現在の出力とも照合します。名前付き出力の結果は各出力のメディア・暗号方式・シグナリング・外部検査を一覧で返し、全体の passed も示します。内容が一致していても、それだけで計画した暗号方式や DRM 宣言を確認できるわけではありません。どちらのモードもライセンス取得を伴う再生の確認は行いません。
